Get started

Five lines, from nothing to an agent that asks the graph first.

  1. Install

    One global binary. Or pnpm add -D zerograph to pin it per project.

    $ npm install -g zerograph

  2. Ignore the store

    The graph is built per checkout and never committed.

    $ echo .zerograph/ >> .gitignore

  3. Build

    The first run downloads the embedding model; after that only changed files are re-read.

    $ zerograph build

  4. Ask

    Plain words in, path:line out. It stays fresh with your edits.

    $ zerograph ask cancellation policy

  5. Wire your agent

    Optional: the Claude Code plugin. Also --codex, --cursor, --copilot, --gemini, --opencode.

    $ zerograph install-agent --claude

How it works

The hard part is not building a better graph, it is building a better door onto it.

A repository's ids, imports and calls already form a dense, human-authored graph. zerograph extracts it and finds the right entry point from a question phrased in ordinary words.

  1. Exact id or symbolA name like FR-PAY-22 or StaffService goes straight to its node.
  2. BM25 over passagesLexical search over what the docs and code actually say.
  3. Local dense listAn embedding model on your machine, interleaved with the lexical list rank by rank.
  4. One hop over the graphThe surviving seeds bring their neighbours, rendered as path:line ID headline.

Worktrees

Each checkout keeps its own graph and index in .zerograph/, so worktrees, clones and branches never share state. The only thing shared is a cache of embeddings. Parallel agents are safe: one writer lock per checkout.

1.5 sto build a clone of zerograph itself, instead of 46 s, with the same answers.

Where it fits, and where it does not

Good at

  • Costing nothing. Build, refresh and query all run locally, for zero API tokens.
  • Short answers. About 200 tokens of path:line, not a dump of files.
  • Ids, symbols and keywords. 40/40 keyword and 12/12 code on the recorded bench.
  • Staying fresh. A session hook refreshes the graph, and a refresh re-reads only the files that changed.
  • Parallel agents. A graph per checkout and one writer lock, so worktrees never wait on each other.
  • Being checkable. The risk label is four fixed thresholds printed with the counts they came from.

Know before you trust it

  • Loose wording misses a third of the time. Paraphrase reads 20/30. ask --rerank helps, and it is the one step that spends tokens.
  • It records only what a file proves. A call through a chained expression or a callback has no edge, so a "nothing uses this" wants an rg -l beside it.
  • Grep is still right for a literal. The graph is for concepts, callers and ids.
  • Three platforms. macOS arm64, Linux x64 and Windows x64.
  • A model download. The first build fetches the embedding model, about 200 MB on disk.
  • Depth varies by language. Swift is read without imports or calls, and Razor is opt-in.

Questions

Does anything leave my machine?

Build, refresh and query all run locally. ask --rerank is the only thing that spends model tokens, and only when asked.

How does it stay fresh?

The agent's session hook refreshes the graph per checkout, and a resident serve polls and re-reads only the files that changed. An answer given while files are behind says so itself. Keeping fresh

Do worktrees and branches share a graph?

No. Each checkout keeps its own graph and index in .zerograph/. The only thing shared is a cache of embeddings, text hash to vector, which is why a new worktree builds in seconds.

Which embedding model does it use?

By default the 4-bit ONNX export of embeddinggemma-300m, run on your machine. Another model can be pinned in zerograph.toml. Embeddings

Does it replace grep?

No. Ask the graph for a concept, a caller or an id; grep is still right for a literal string.
